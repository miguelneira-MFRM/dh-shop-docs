§ 01 — PurposeWhat this API is

The Matches API turns quiz answers into ranked mattress recommendations plus foundation mappings for the Matches tab. The browser never calls Recommender V2 directly.

ConcernOwner
Quiz → request bodyClient (formatNewRecommendationsPayload, optional try-in-store stamp)
Validation, upstream call(s), foundation mappingsBFF (/api/matches)
Ranked products + log idRecommender V2
Three match cardsClient (mapNewQuizResponseToMatches)
Record top items seenSibling POST /api/updateTopItems

Legacy contrast: V1 uses POST /api/recommendedProducts. New DH Shop work targets /api/matches only.

§ 02 — InitWhen it runs (and when it does not)

On Matches tab mount, resolveMatchesInitAction runs once (tab switches do not re-run):

Init actionWhenNetwork
skipskipInitialFetch setNone
profile-preloadFirst View Matcher + prior profile log; quiz not just submittedNone
restore-cacheSession has recommenderLogId; quiz not just submittedNone
fetchFresh quiz submit, or no cache/preloadPOST /api/matches

QA pitfall

Returning to the Matches tab from PLP with an existing session log often shows no /api/matches call — that is expected cache restore, not a broken network. Quiz re-submit always forces fetch.

§ 03 — LifecycleEnd-to-end lifecycle

Step-by-step flow

  1. Sleep Expert completes quiz and clicks View Matches! (or refresh / re-edit fetch path).
  2. Init resolves to fetch (or cache/preload skips the rest).
  3. Client builds MatchesRecommendationsPayload from quiz answers + store/customer identifiers. Accessory size mapping must already be loaded.
  4. If enableMatchesBudgetToggleNewDesign is on, client may stamp isAvailableTryInStore.
  5. Client POSTs to /mattressmatcher/api/matches with query flags.
  6. BFF rejects bad method / old-quiz reason / missing mattress size.
  7. BFF calls Recommender V2 once (non-budget) or twice sequentially (budget), then builds result with foundation mappings.
  8. Client maps products → three pairings; caches response ~1 hour in memory.
  9. Fire-and-forget POST /api/updateTopItems.

§ 05 — BFFBFF inner workings

Helper bodies in utils/api/matches.ts are not fully present in the current context dump. Behavior below is from the route handler and curated overlays.

Non-budget / single-call

Used when there is no budget value or enableMatchesBudgetToggleNewDesign === 'false':

  1. Strip sizes from upstream body (sizes kept for result build).
  2. One Recommender V2 call.
  3. buildMatchesResult → if null, echo upstream status/message.
  4. Success: { recommendedProducts, recommenderLogId, mappings }.

Budget dual-call

Used when budget value exists and the new-design flag is not forced off:

  1. Default call — budget fields removed. Failure stops the flow.
  2. Budget call — sets inbound log from default; forces FITS_YOUR_BUDGET, edit action, isBudgetSelected: true.
  3. Budget failure → graceful degrade to default-only products.
  4. Both succeed → merge: first 6 default products + all budget products.

QA pitfall: Best Matches / Fits Your Budget in the UI usually does not fire a second /api/matches — it re-indexes the fetched list and calls updateTopItems. The dual-call happens inside the original matches request when budget was in the quiz payload.
